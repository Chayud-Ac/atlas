# M5: Azure (shared + dev) Implementation Plan

> **How this plan was executed:** the user asked to finish M5 in one session. Claude checked the subscription first (read-only), the user made two decisions (region and scope), and Claude built and ran everything, pausing for approval before creating any Azure or Entra resource. Unlike M4a and M4b, this file is mostly a record: the code itself is in the PR.

**Goal:** A merge to `main` builds one image per app, deploys it to Azure Container Apps in dev, and smoke-tests it. Sign-in with Entra ID works in dev. No credentials exist anywhere.

**Architecture** (spec §3–§8, §15):

- **`rg-atlas-cicd`:** the pipeline identities, with federated credentials (ADR 0004).
- **`rg-atlas-shared`:** the registry.
- **`rg-atlas-dev`:**
  - a VNet-integrated Container Apps environment, with the web app public and the API internal
  - the migration job
  - Postgres 17 with Entra authentication only (public endpoint in dev)
  - Log Analytics
- **`bootstrap.sh shared|dev`** creates what only a human may create. `deploy.yml` and `deploy-env.yml` do everything else.

## Deviations from the spec (all deliberate)

1. **Region:** `japaneast`, with `malaysiawest` as the fallback, instead of `southeastasia`/`eastasia` (ADR 0017).
2. **IDs are GitHub secrets, not variables** (ADR 0004). Variables would print in public logs, and `::add-mask::` on a `${{ }}` value is unreliable (actions/runner#643). There are still no credentials.
3. **Only `dev` is in `environments.json`.** UAT and prod need other regions, because of the quota of one Container Apps environment per region. That's an M6 decision.
4. **App Insights and Postgres diagnostic settings wait for M7.** The Container Apps environment does send its logs to Log Analytics now: the migration job's logs are needed to debug deploys.
5. **The API's internal ingress allows plain HTTP** (`allowInsecure: true`). nginx calls `http://ca-atlas-api-dev` inside the environment, and the ingress stays internal-only.
6. **`what-if` compares each template using the parameters of its last deployment,** read from Azure, so no ID needs to be a PR-readable value. On the first PR, environments not yet deployed are reported as "not deployed yet".
7. **`db-access.sh` waits for M7,** with the runbooks.

## Execution notes (2026-10-17)

M5 is done: PR #10 merged as `cdd4d4e`, and the first `deploy.yml` run was green end to end. The user signed in to dev with their university account, saw their name in the header, and added and deleted notes. What happened along the way:

1. **The read-only subscription checks changed the plan before any code was written.**
   - The offer's region policy denies `southeastasia`.
   - The subscription allows one Container Apps environment per region.
   - Both are recorded in ADR 0017, and the user chose `japaneast`.
2. **`bootstrap.sh dev` took 11 minutes** (`shared` took under 3). Most of that was `az` waiting on Entra while new app registrations, service principals and the group replicated. Every step is idempotent, so a slow run is safe to repeat.
3. **IDs moved from variables to secrets before any workflow ran** (ADR 0004).
   - Variable values appear in plain text in step headers, and `::add-mask::` on a `${{ }}` value is unreliable (actions/runner#643).
   - The values were moved in place: read from the variable, written to the secret, never printed. `bootstrap.sh` now writes secrets.
   - The scan of the public `what-if` and deploy logs found no Azure ID. The only GUID-shaped strings were GitHub's runner internals.
4. **The spec's `pgaadauth` risk was real.**
   - A temporary firewall rule for the workstation, then a connection as a db-admins member, showed `pgaadauth_create_principal_with_oid` in `postgres` and **not** in `atlas`. M2's migration job would have failed on its first Azure run.
   - The same check showed the migrator may create schemas in `atlas`, which `azure_pg_admin` owns.
   - The fix was test-first: an integration test installs a stand-in function in the test container's `postgres` database only, fails with `role "id-atlas-api-test" does not exist`, and passes once the job creates the role through a second pool connected to `postgres`.
   - The firewall rule was removed straight after the check.
5. **The first `what-if` failed with `AADSTS700213`.** This repo's OIDC tokens use GitHub's immutable subjects (`repo:<owner>@<owner id>/<repo>@<repo id>:…`), not `repo:<owner>/<repo>:…`. `bootstrap.sh` now reads the prefix from `GET /repos/{repo}/actions/oidc/customization/sub`, and the three federated credentials were updated.
6. **CI's shellcheck flagged SC2015** (`A && B || C`) in `teardown.sh`, which the local shellcheck 0.11.0 doesn't report. It's now an `if`.
7. **What-if shows server-side defaults as deletions** (for example `properties.environmentMode` on the Container Apps environment). That's Azure's documented "noise"; real changes stand out against it.
8. **The first pipeline deploy re-ran `platform.bicep` as `id-atlas-github-dev`.** That proved its least-privilege roles are enough, including the AcrPull grant on `rg-atlas-shared` through the conditioned RBAC Administrator role.
9. **The dev deploy took 7 minutes:** platform, migration job, apps, smoke tests. All five smoke tests passed, including "the API runs version `cdd4d4e…`" and "the API is ready (it can reach Postgres)".
10. **`main` now requires 9 checks.**
11. **Running costs:** Postgres B1ms is about $0.60 a day, and everything else is close to $0 while idle. Run `scripts/teardown.sh all` when the project is finished.
