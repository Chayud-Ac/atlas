# M6: UAT and prod Implementation Plan

> **How this plan was executed:** as with M5, Claude checked the subscription first, then built and ran everything, after the user approved the cost. Halfway through, a hard subscription limit forced a redesign, and the user chose its direction. The two approvals in the first promotion are clicked by the user. This file is mostly a record; the code is in the PR.

**Goal:** A merge to `main` deploys one image to dev, then promotes **the same SHA** to UAT and prod after approval, and ends with a GitHub Release (spec §3.2). UAT and prod have private Postgres networking, prod keeps a warm replica and a delete lock, and nobody has database access in UAT or prod by default.

**Architecture (as built, ADR 0017):**

- **`rg-atlas-shared`** holds what every stage shares:
  - the registry
  - `vnet-atlas-shared`, with `snet-cae` plus a delegated Postgres subnet per private stage
  - `log-atlas-shared`
  - **the one Container Apps environment, `cae-atlas`**
- **Each `rg-atlas-{dev,uat,prod}`** (all `japaneast`) holds the stage's own resources:
  - its workload identities
  - its Postgres: public in dev; in UAT and prod, private in the stage's subnet of the shared VNet, with a private DNS zone (ADR 0008)
  - its apps and migration job, which run in the shared environment
- **`deploy.yml` runs dev → uat → prod → release.** UAT and prod reuse `deploy-env.yml`, and their GitHub environments require the repo owner's approval.
- **`bootstrap.sh` reads per-stage flags from `environments.json`:** `requiresApproval`, `deleteLock`, `humanDbAccess` and `localhostRedirect`.
- **Stage pipelines get "Atlas Environment Joiner" on `rg-atlas-shared`:** join the environment, a subnet or the VNet, and nothing else.

## Decisions (the user's)

1. **Go ahead with M6** at about $1.70 a day extra: two more Postgres B1ms servers, and prod's minimum of one replica per app.
2. **After the limit was found:** share one Container Apps environment, with **private** databases for UAT and prod, rather than public databases or stopping.
3. **Follow-up, after M6:** move resource names into an exported `infra/shared/naming.bicep`, and give `environments.json` a type in `types.bicep`. That came from the user's question about the usual Bicep layout. The four entry points and `environments.json` stay; the reasons are in the execution notes.

## Deviations from the spec

1. **One shared Container Apps environment and VNet, in `japaneast`** (ADR 0017), instead of one per environment in `southeastasia`. Stages are isolated by identity, not by network (ADR 0008).
2. **Prod alerts, availability tests and `ALERT_EMAIL` wait for M7,** with the rest of observability.
3. **One log workspace for all stages' app logs.** Per-stage Application Insights comes with M7.

## Execution notes

1. **The first UAT and prod platform deploys failed at validation** with `MaxNumberOfGlobalEnvironmentsInSubExceeded`: the subscription may have only **one** Container Apps environment in total. The per-region usage API had reported "1 per region", which isn't the binding limit. Nothing was created. The user chose the shared-environment redesign with private databases.
2. **`bootstrap.sh shared`'s first re-run failed in `az role definition update`** (`KeyError: 'roleName'`). The update path had never run in M5, because the roles were only ever created. Updates now take the role in the shape `az role definition list` returns.
3. **Why the Bicep keeps four entry points and `environments.json`** rather than the common `main.bicep` with per-environment `.bicepparam` files:
   - The pipeline runs the migration job and waits for it **between** `platform` and `apps`, which one declarative deployment can't do.
   - Each template is deployed by a different least-privilege identity.
   - `environments.json` is read by both Bicep (`loadJsonContent`, Microsoft's shared variable file pattern) and the scripts (`jq`).
   - Exported naming functions and types are the real gap, and they're the follow-up above.
